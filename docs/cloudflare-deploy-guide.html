Cloudflare 자동 배포 가이드

git push 한 번으로 웹 화면, API, DB 마이그레이션까지 Cloudflare Worker에 배포되도록 설정하는 순서입니다.

기준: Cloudflare 대시보드의 Workers Builds(Git 연결) 화면, 2026년 11월. 메뉴 이름은 영어 원문을 이렇게 표시했습니다. Cloudflare가 화면을 바꾸면 이름이 조금 다를 수 있습니다.

1전체 구조와 배포 흐름

Worker 하나가 웹 화면(정적 파일), API(/api/*), 공개 미디어(/media/*)를 모두 맡습니다. 코드는 저장소의 apps/edge(Worker)와 apps/web(화면)입니다.

main 브랜치에 push하면 일어나는 일

git push→Cloudflare가 저장소를 받음→npm ci (apps/edge)→빌드: 웹 화면 빌드→배포: D1 마이그레이션 → Worker 배포
  • 빌드 명령 npm run build:web은 apps/web을 빌드해 apps/web/dist를 만듭니다.
  • 배포 명령 npm run deploy:ci는 새 DB 마이그레이션을 운영 D1에 적용한 뒤 wrangler deploy로 Worker와 화면 파일을 올립니다.
  • 마이그레이션이나 빌드가 실패하면 배포하지 않고 멈춥니다. 사이트는 이전 버전 그대로입니다.
이름종류용도
artist-portfolioWorker사이트 전체. 이름은 apps/edge/wrangler.jsonc의 name과 같아야 합니다
artist-portfolioD1 데이터베이스작품, 문의, 관리자 등 모든 데이터
artist-originalsR2 버킷 (비공개)사진 원본
artist-publicR2 버킷 (공개용)웹용 사진, 영상, 영상 포스터. Worker가 /media/*로 내보냅니다

2시작 전에 확인할 것

  • Cloudflare 계정이 Workers Paid 플랜(월 $5)입니다. 대시보드 왼쪽 Workers & Pages → Plans
  • 사이트 도메인이 Cloudflare에 등록되어 있습니다(지금 Tunnel에 쓰는 도메인이면 됩니다).
  • 내 PC에 Node.js 22 이상이 있습니다. node -v로 확인합니다. Wrangler(Cloudflare 도구)가 22 이상을 요구합니다.
  • cloudflare-migration 브랜치의 작업이 main에 합쳐져 있습니다. 자동 배포는 main 브랜치를 기준으로 하고, main에 apps/edge가 없으면 빌드가 실패합니다.
순서가 중요합니다. 도메인을 Worker에 연결하기(9단계) 전까지는 사이트가 계속 지금의 집 PC(Docker + Tunnel)에서 운영됩니다. 그 전 단계는 몇 번을 다시 해도 방문자에게 영향이 없습니다.

내 PC에서 Cloudflare에 로그인해 둡니다. 브라우저가 열리면 허용을 누릅니다.

cd apps/edge
npm ci
npx wrangler login

3D1, R2 만들기

한 번만 합니다. 명령어 쪽이 빠르고, 대시보드로 해도 결과는 같습니다.

명령어로 (권장)

cd apps/edge
npx wrangler d1 create artist-portfolio --location apac
npx wrangler r2 bucket create artist-originals
npx wrangler r2 bucket create artist-public
  • d1 create가 출력하는 database_id(UUID)를 복사해 둡니다. 다음 단계에서 씁니다.
  • --location apac은 DB를 아시아 태평양에 둡니다. 한국 방문자와 가까워 빠르고, 만든 뒤에는 위치를 바꿀 수 없습니다.

대시보드로

  1. Storage & databases → D1 SQL database → Create Database. 이름 artist-portfolio, 위치는 Asia-Pacific. 만든 뒤 상세 화면의 Database ID를 복사합니다.
  2. Storage & databases → R2 object storage → Create bucket. artist-originals, artist-public 두 개를 만듭니다. 두 버킷 모두 Public access를 켜지 않습니다(공개 파일도 Worker를 거쳐 나갑니다).
이미지 변환(Cloudflare Images)은 따로 만들 것이 없습니다. Worker 설정의 images 바인딩으로 바로 씁니다. 한 달 5,000건까지 무료이고, 사진 한 장당 최대 6건을 씁니다.

4wrangler.jsonc 값 채우기

apps/edge/wrangler.jsonc에서 두 곳을 실제 값으로 바꾸고 커밋합니다.

항목지금 값바꿀 값
d1_databases[0].database_id00000000-0000-…3단계에서 복사한 Database ID
vars.PUBLIC_ORIGINhttps://example.com실제 사이트 주소. 예: https://myname.com (끝에 / 없이)
PUBLIC_ORIGIN이 실제 주소와 한 글자라도 다르면 관리자 로그인 후 저장, 업로드 같은 모든 변경이 403 "허용되지 않은 Origin입니다"로 막힙니다. www를 쓰는지, https인지 확인하세요.
git add apps/edge/wrangler.jsonc
git commit -m "Cloudflare 운영 DB ID와 도메인 설정"
git push origin main

이 push는 아직 저장소를 연결하기 전이라 아무것도 배포하지 않습니다.

5배포용 API 토큰 만들기

Workers Builds가 자동으로 만드는 기본 토큰에는 D1 권한이 없습니다. 배포 때 DB 마이그레이션까지 하려면 D1 권한을 넣은 토큰을 직접 만들어 연결해야 합니다.

  1. 오른쪽 위 사람 아이콘 → Profile → 왼쪽 API Tokens → Create Token.
  2. 맨 아래 Custom token의 Get started를 누릅니다.
  3. Token name: artist-portfolio Workers Builds
  4. Permissions에 아래 7줄을 추가합니다(+ Add more로 줄 추가).
    구분항목권한
    AccountWorkers ScriptsEdit
    AccountD1Edit
    AccountWorkers R2 StorageEdit
    AccountAccount SettingsRead
    ZoneWorkers RoutesEdit
    UserUser DetailsRead
    UserMembershipsRead
  5. Account Resources: Include → 내 계정. Zone Resources: Include → Specific zone → 사이트 도메인.
  6. Continue to summary → Create Token. 토큰 값은 이 화면에서만 보이지만, Workers Builds에서는 목록에서 고르기만 하면 되므로 따로 적어 둘 필요는 없습니다.
기본 토큰 권한(Workers Scripts, KV, R2, Account Settings, Workers Routes, User Details, Memberships)에 D1 Edit을 더한 구성입니다. KV는 이 사이트에서 쓰지 않아 뺐습니다. Workers Builds는 현재 사용자 토큰만 지원합니다(계정 토큰은 아직 미지원).

6GitHub 저장소 연결

  1. 대시보드 왼쪽 Workers & Pages → Create application.
  2. GitHub를 고릅니다. 처음이면 GitHub 화면이 열리고 Cloudflare Workers and Pages 앱 설치를 묻습니다. Only select repositories로 이 저장소만 허용하는 것을 권장합니다.
  3. 저장소 목록에서 이 저장소를 고릅니다(검색창 사용 가능).
  4. 설정 화면을 아래 표처럼 채웁니다. Root directory는 Advanced settings를 펼쳐야 보일 수 있습니다.
    항목값설명
    Project nameartist-portfolioWorker 이름. wrangler.jsonc의 name과 반드시 같아야 합니다
    Build commandnpm run build:web웹 화면을 빌드합니다
    Deploy commandnpm run deploy:ciD1 마이그레이션 후 배포. 기본값 npx wrangler deploy를 바꿉니다
    Root directoryapps/edgeWorker 설정과 package.json이 있는 곳
    API token5단계에서 만든 토큰기본 토큰이면 마이그레이션 단계가 권한 오류로 실패합니다
    Build variables비워 둠Node 버전은 apps/edge/.nvmrc(22)로 정해져 있습니다
  5. Save and Deploy를 누르면 첫 빌드가 시작됩니다. 3~5분 걸립니다.
이미 wrangler deploy로 Worker를 만들어 둔 경우에는 Workers & Pages → artist-portfolio → Settings → Builds → Connect로 같은 값을 넣습니다.

첫 배포가 성공해도 아직 접속 주소가 없습니다(운영 Worker는 workers.dev 주소를 꺼 두었습니다). 정상입니다. 도메인은 9단계에서 연결합니다.

7빌드 설정 다듬기

Workers & Pages → artist-portfolio → Settings → Build(화면에 따라 Builds)에서 합니다. 저장한 설정은 다음 빌드부터 적용됩니다.

Branch control

  • 운영 브랜치(Production branch)가 main인지 확인합니다.
  • Enable Preview Builds는 끕니다. 다른 브랜치를 push하면 미리보기 버전이 만들어지는데, 이 버전도 운영 DB와 버킷을 그대로 씁니다. 테스트 데이터가 운영에 섞일 수 있습니다. 리허설은 12단계의 스테이징을 씁니다.

Build watch paths

문서만 고친 push로 빌드가 돌지 않게 합니다(빌드 시간 절약).

항목값
Include pathsapps/edge/*, apps/web/*
Exclude paths비워 둠
빌드 한도: 유료 플랜은 월 6,000분, 빌드 1회 최대 20분입니다. 이 사이트의 빌드는 보통 5분 안에 끝납니다.

8비밀 키와 관리자 계정

APP_SECRET_KEY 넣기

로그인 시도 기록과 문의 기록의 식별값을 만드는 비밀 키입니다. 코드나 wrangler.jsonc에 쓰지 않습니다.

cd apps/edge
openssl rand -hex 32              # 나온 값을 복사
npx wrangler secret put APP_SECRET_KEY

대시보드로 하려면 Settings → Variables and Secrets → + Add → Type: Secret, 이름 APP_SECRET_KEY. 비밀 값은 저장 즉시 새 버전으로 반영됩니다.

관리자 계정 만들기

cd apps/edge
npm run create-admin -- 내이메일@example.com
  • 비밀번호(10자 이상)를 두 번 입력합니다. 화면에 보이지 않습니다.
  • 같은 명령을 다시 실행하면 비밀번호가 바뀌고 기존 로그인은 모두 끊깁니다(비밀번호를 잊었을 때도 이 명령).
도메인 연결 전에 반드시 관리자를 만드세요. 관리자가 없는 상태로 공개하면, 처음 들어온 사람이 "관리자 계정 설정" 화면에서 관리자가 될 수 있습니다.

9도메인 연결 (전환)

여기서부터 방문자가 새 사이트를 보게 됩니다. 방문자가 적은 시간에 합니다. 끊기는 시간은 보통 1~2분입니다.

① Tunnel이 쓰던 주소 비우기

  1. Zero Trust → Networks → Tunnels → 쓰던 터널 → Public Hostname(또는 Published application routes)에서 사이트 도메인 항목을 지웁니다.
  2. 도메인 → DNS → Records에서 같은 이름의 CNAME(…cfargotunnel.com)이 남아 있으면 지웁니다. 같은 이름의 레코드가 있으면 Worker 도메인 연결이 실패합니다.

② Worker에 도메인 붙이기

설정 파일로 관리하면 다음 배포 때도 그대로 유지됩니다. apps/edge/wrangler.jsonc의 맨 위 설정("observability" 근처)에 추가하고 push합니다.

"routes": [{ "pattern": "myname.com", "custom_domain": true }],
git commit -am "운영 도메인을 Worker에 연결" && git push origin main

대시보드로 하려면 Workers & Pages → artist-portfolio → Settings → Domains & Routes → + Add → Custom domain → 도메인 입력 → Add Custom Domain. DNS 레코드와 인증서는 Cloudflare가 자동으로 만듭니다. 이 방법을 썼더라도 위 routes를 설정 파일에 같이 적어 두는 것을 권장합니다.

www.myname.com도 쓰려면 routes에 한 줄 더 추가하고, PUBLIC_ORIGIN은 대표 주소 하나만 둡니다. 다른 주소는 Rules → Redirect Rules로 대표 주소로 보냅니다.

③ 확인

curl -fsS https://myname.com/api/v1/health/ready
  • {"status":"ready"}가 나옵니다.
  • 첫 화면, 작품 목록, 작품 상세가 열립니다. 새로고침해도 404가 나지 않습니다.
  • /admin에서 8단계 관리자로 로그인되고, 작품 저장이 됩니다.
  • 사진 하나, 영상 하나를 올려 화면에 보이고 영상이 재생됩니다.
  • 문의 페이지에서 문의를 보내고 관리자 화면 문의에 들어옵니다.
  • 전체 점검은 수동 테스트 시나리오를 따릅니다.

문제없으면 집 PC의 Docker 스택은 docker compose stop으로 중지만 해 둡니다(지우지 않음). 1주일 정도 지켜본 뒤 정리합니다.

10보호 설정: 속도 제한, 결제 알림

WAF 속도 제한

로그인 무차별 대입과 문의 폭주를 Worker까지 오기 전에 막습니다(Worker CPU 요금도 막는 효과).

  1. 도메인 → Security → Security rules(이전 화면에서는 WAF → Rate limiting rules) → Create rule → Rate limiting rules.
  2. 규칙 1: URI Path equals /api/v1/auth/login, 같은 IP 기준 10초에 5회 초과 시 Block, 10초 동안.
  3. 규칙 2: URI Path equals /api/v1/inquiries 그리고 Request Method POST, 같은 IP 기준 10초에 3회 초과 시 Block.

무료·Pro 도메인에서 쓸 수 있는 규칙 수와 기간 옵션은 플랜마다 다릅니다. 규칙이 하나만 허용되면 로그인 규칙을 먼저 만듭니다. 앱 안에도 이메일·IP별 5회 실패 시 15분 잠금이 있습니다.

결제 알림

  1. Manage Account → Notifications → Add.
  2. Usage Based Billing을 고르고, Workers, R2, Images 사용량에 알림 기준을 정합니다.

예상 비용은 월 $6~7 정도입니다(이전 검토 문서 참고).

원본 백업

D1은 Time Travel로 30일 안의 시점으로 되돌릴 수 있습니다. R2에는 그런 기능이 없으므로 사진 원본(artist-originals)은 rclone 등으로 주기적으로 개인 PC나 외장 디스크에 복사해 둡니다.

11평소 사용법과 되돌리기

배포

git push origin main

진행 상황은 Workers & Pages → artist-portfolio → Deployments에서 봅니다. 아래 View Build History에 빌드마다 로그가 남습니다(90일 보관). GitHub에서도 커밋 옆에 빌드 결과가 표시됩니다.

배포 전 내 PC에서 확인

cd apps/edge
npm run typecheck && npm test     # Worker 테스트 (로컬 D1, R2 사용)
npm run build:web                   # 화면 빌드

자동 배포는 테스트를 돌리지 않습니다. 빌드 시간을 줄이려고 뺐으므로 push 전에 위 명령으로 확인합니다. 빌드 때도 테스트를 돌리려면 Build command를 npm test && npm run build:web으로 바꿉니다.

DB 구조를 바꿀 때

  • apps/edge/migrations/에 다음 번호의 파일을 만듭니다: npx wrangler d1 migrations create artist-portfolio 설명
  • 마이그레이션은 배포 직전에 적용되므로 컬럼 추가, 기본값 지정처럼 기존 코드가 계속 동작하는 변경만 합니다. 컬럼 삭제나 이름 변경은 코드 배포 후 다음 마이그레이션에서 합니다.
  • 내 PC에서 먼저: npm run db:migrate:local

문제가 생겼을 때 되돌리기

대상방법
코드Deployments에서 이전 버전의 ⋯ → Rollback. 또는 npx wrangler rollback. 그다음 원인 커밋을 git revert로 되돌리고 push합니다(안 그러면 다음 push 때 다시 배포됩니다)
DBnpx wrangler d1 time-travel info artist-portfolio --timestamp 2026-11-01T03:00:00Z로 시점의 bookmark를 얻고 npx wrangler d1 time-travel restore artist-portfolio --bookmark <값>. 그 시점 이후 데이터(새 문의 등)는 사라집니다
도메인 전체최악의 경우: Worker의 도메인을 지우고 Tunnel의 Public Hostname을 다시 만들고 docker compose start. 그 사이 새 사이트에 들어온 문의와 업로드는 옮겨지지 않습니다

12스테이징으로 리허설 (선택)

운영과 완전히 분리된 DB와 버킷으로 https://artist-portfolio-staging.<계정>.workers.dev에 띄워 봅니다. 자동 배포와 별개로 내 PC에서 배포합니다.

cd apps/edge
npx wrangler d1 create artist-portfolio-staging --location apac
npx wrangler r2 bucket create artist-originals-staging
npx wrangler r2 bucket create artist-public-staging
# wrangler.jsonc의 env.staging에 database_id와 PUBLIC_ORIGIN(workers.dev 주소)을 넣는다
npx wrangler secret put APP_SECRET_KEY --env staging     # 운영과 다른 값
